# 排期审查与 CPM 重算用户及测试手册

本手册面向使用“排期审查”页面的业务人员、项目计划人员、测试人员和试点组织者，说明如何查看直接 Canonical 或外部 JSON 导入形成的来源快照、理解审查问题、生成 CPM 重算方案、判断关键任务与浮时、记录接受或拒绝意见，并通过统一用例收集用户反馈。

> 当前版本是“受限 CPM 工程能力”：在明确支持的输入范围内提供确定性计算和人工审阅，不是 Microsoft Project 的完整替代品，也不代表已经通过生产通用性验收。

## 0. 一页式操作与测试清单

### 业务人员如何使用

1. 登录后进入左侧“排期审查”，点击“导入排期”。
2. 选择已经由来源系统处理完成的 JSON；当前不能直接上传 MPP。
3. 导入成功后选择来源快照，先核对项目、版本、任务数、依赖数和“只读来源快照”。
4. 分别查看“外部接入”“来源审查”“CPM 重算”，不要把接入成功理解成一定可以重算。
5. 逐条查看 blocker/warning；汇总任务或 inactive 依赖必须先进入“确认关系”，选择明确的 active 叶子任务。
6. CPM 允许时点击“生成重算方案”；有明确工期授权时点击“工期目标优化”。
7. 在 Candidate 中核对完成时间、任务日期、浮时、关键标识、约束/资源问题和方案对比甘特。
8. 填写有业务依据的审阅意见，再接受或拒绝。接受只记录态度，不会修改来源计划。
9. 查看 Delivery 时确认 `application_allowed`；出现 `DELIVERY_ADAPTER_UNAVAILABLE` 表示结果可审阅但当前不能自动回写。

### 测试人员如何执行

1. 先完成 API `5050`、Web `5173` 和 Provisioner `8002` 健康检查；需要 AI 审查时还要确认 Worker 正在消费任务。
2. 使用一个受支持样例、一个明确阻断样例和一个脱敏真实项目，禁止只用合成数据宣布业务通过。
3. 先跑 Schedule 单元测试，再跑真实 API 集成测试；涉及 Agent 时补跑 E2E。
4. 跑前端排期测试、ESLint、Web Build 和 Docs Build。
5. 执行 C01–C08 冻结套件和 v2.8 Oracle，禁止修改 expected 来让失败变绿。
6. 按 UAT-01 起逐项记录截图、项目版本、实际结果和问题编号，最后填写测试完成报告。

完整命令见[自动化测试执行](#_15-自动化测试执行)，人工验收见[用户验收测试用例](#_11-用户验收测试用例)。

## 2. 功能能做什么

### 2.1 当前已支持

在受支持的来源快照上，系统可以：

- 保存并展示不可变的来源排期快照；
- 在“排期审查”页面选择处理完成的 JSON，自动识别来源格式或严格 Canonical 并提交；
- 接收已注册格式的版本化来源 JSON，保留来源证据并生成严格内部 Canonical；
- 独立统计任务、依赖、开放起点和开放终点；
- 显示确定性的审查问题、严重等级、对象证据和直接上下游；
- 从当前快照进入整份计划 AI 审查，对已有 Audit、Issue 和 Capability 进行汇总、解释和证据导航；
- 在统一项目日历下计算任务的最早开始、最早完成、最晚开始和最晚完成；
- 计算总浮时和自由浮时；
- 标记关键活动任务；
- 处理 FS、SS、FF、SF 四类关系的零 Lag、正 Lag 和负 Lag；
- 处理 ASAP、SNET、FNET、MSO、FNLT 约束；
- Deadline 和项目 required finish 作为管理目标产生偏差 Issue，不直接移动任务；
- MSO 与网络冲突时保留固定开始，并输出 `HARD_CONSTRAINT_NETWORK_CONFLICT` 证据；
- FNLT 与网络冲突时，当前 v12 保留网络计算日期并输出 `FINISH_CONSTRAINT_VIOLATED`，不会为了满足上界而让任务越过前置关系；
- 在 Canonical v2.6 / Profile v13 下固定 COMPLETED 任务的 actual start/finish，以实际完成约束后续 NOT_STARTED 任务，并按任务有效日历输出 Baseline 0 开始/完成偏差；存在 IN_PROGRESS 时使用 Profile v14，固定 actual start，从状态日期与网络要求边界之后排 remaining work，并用预测完成约束后续；
- 在 Canonical v2.7 下于 CPM 完成后只读检测资源超配，并输出 Assignment 工作分钟和成本数值；资源分析不会修改 CPM 日期；
- 在 Canonical v2.8 / Profile v15 下保留 inactive 来源日期并将其标记为“不参与重算”；inactive 不进入 CPM、关键路径、汇总滚动、资源分析或工期优化；
- 处理自动任务、当前 Profile 支持的手工任务和显式 locked 任务；页面当前不提供任务锁定选择，locked 范围由系统接口调用方传入；
- 按任务层级自底向上滚动汇总任务日期；
- 处理零工期里程碑，并保证里程碑的开始与完成时刻相等；
- 生成独立的重算方案，供用户接受或拒绝；
- 在不修改来源快照的前提下查看交付内容。

### 2.2 当前不支持

遇到下列输入时，系统应明确显示阻断原因，不会生成近似结果：

- 未明确任务有效日历或后续任务 Lag 日历策略的多/任务日历，以及未知父日历、继承环、无工作时间、日期范围冲突或时区不一致的日历例外；
- 未经 Dependency Workbench 明确确认的汇总任务依赖或 inactive 任务依赖；
- 从完成百分比反推 IN_PROGRESS 的剩余工期；v14 必须使用来源显式提供的 remaining duration；
- 当前 Profile 以外的约束组合或不合法任务层级；
- 自动资源均衡、资源成本优化；
- 多项目统筹；
- MPP/XML 文件直接解析或回写。

“不支持”不是计算失败。它表示系统识别到输入超出已验证范围，为避免输出看似合理但实际错误的日期，主动停止计算。

### 2.3 四个必须记住的边界

1. **来源快照始终只读**：生成、接受或拒绝方案都不会原地修改来源任务。
2. **前端不计算排期**：页面只展示后端 `engine_result` 的确定性结果。
3. **接受不等于应用**：接受只记录用户对当前方案的态度；正式业务计划是否产生新版本，仍由受控交付和业务适配流程决定。
4. **FNLT 尚未声明与 Microsoft Project 完全一致**：独立 Project 16.0 观测会让 FNLT 优先于 FS 网络并提前任务；Yuxi 当前采用保留网络、报告违反的安全口径，该差异仍待业务评审。

## 3. 五分钟快速体验

### 第一步：进入排期审查

登录系统，在左侧导航点击“排期审查”。页面左侧应出现“来源快照”列表。

如果列表为空，可以点击页面右上角“导入排期”，选择处理完成的 JSON。页面会自动识别版本化来源 JSON 或 `canonical_schedule_v2.2` 至 `canonical_schedule_v2.8`，预填外部项目、快照和版本身份；确认后点击“校验并导入”。页面不接受 MPP。

如果导入后仍为空，请确认：

- 当前登录账号是否是提交快照的账号；
- 业务系统或测试准备人员是否已经提交快照；
- 页面是否显示加载或权限错误。

### 第二步：选择来源快照

在左侧选择一个用于体验的快照。建议由测试组织者提供名称中包含“演示”“脱敏”或“UAT”的快照，避免误选真实生产数据。

选择后，主区域应显示：

- 项目名称；
- 任务和依赖数量；
- “只读来源快照”标识；
- 日期关系检查统计；
- 能力边界；
- 审查问题列表。

### 第三步：使用 AI 审查整份计划

在“审查问题”标题栏点击“AI 审查计划”，选择同时具备三个 Schedule 工具的智能体。页面进入绑定当前 Snapshot ID 和内容哈希的新对话，显示外部项目、外部版本和 Snapshot 简写，并预填一个审查问题；预填内容和“建议问题”菜单都不会自动发送，确认后由用户发送。

AI 只能汇总和解释 Yuxi 已持久化的 Audit、Issue 和 Capability，不会直接读取完整来源 JSON 后自行发现新问题。回答具体问题时应提供 Issue 证据链接；没有规则和版本证据时，施工顺序、养护时间、设备到货等专业合理性仍需业务人员确认。

AI 先解释阻断当前目标的 Capability，再按 Issue 严重等级组织问题。同级排序没有量化依据时必须标记为“建议”，不能描述成确定性优先级。

### 第四步：理解外部 JSON 接入边界

如果快照来自 `/api/schedule/imports`，页面会显示三个独立状态：

- “外部接入”：来源 JSON 是否已经校验、适配并保存；
- “来源审查”：Yuxi 是否能够执行确定性 Audit；
- “CPM 重算”：完整语义是否落在受支持的计算范围内。

同时核对来源格式、Adapter 版本、保留字段数量、未参与审查/计算的字段数量和 unsupported 原因。页面不会展示来源未知字段的完整值。

“来源审查允许”只说明 Yuxi 能审查 Adapter 生成的内部 Canonical，不代表 Yuxi 已重新打开 MPP、复算 MPP 哈希或验证外部提取程序。MPP 与来源 JSON 的一致性仍由外部转换服务、manifest 和独立验收负责。

直接提交 Canonical 的旧快照不显示这张 Import 卡片，这是正常兼容行为。

### 第五步：确认 CPM 是否允许

在“能力边界”中查看“CPM 重算”：

- 显示“允许”：可以继续生成重算方案；
- 显示原因代码：可以点击生成按钮查看结构化阻断信息，但不应期待近似结果。

### 第六步：生成重算方案

点击“生成重算方案”。

受支持时，系统打开“排期重算方案审阅”抽屉；超出范围时，页面显示“系统未生成近似结果”及阻断对象。

### 第七步：完成三个判断

在重算方案中回答：

1. 哪些活动任务是关键任务？
2. 哪个非关键任务具有浮时，可以在多大范围内移动？
3. 来源计划与重算计划的完成日期是否发生变化？

完成判断后填写“审阅意见”，点击“接受”或“拒绝”。

## 4. 重要概念

| 概念 | 页面含义 | 用户需要关注什么 |
| --- | --- | --- |
| 外部接入 | 来源 JSON 已通过对应 Adapter 形成内部 Canonical | 接入成功不等于提取过程可信，也不等于全部语义可计算 |
| 外部来源文档 | Import 时保存的来源 JSON 数据语义副本 | 普通页面不展示正文；它不是原始 HTTP 字节或 MPP 文件 |
| Canonical 来源快照 | Adapter 生成、供 Yuxi Audit 和 Candidate 使用的严格 Canonical | 它始终只读，是 Yuxi 内部比较基线，不等同于未经转换的原始事实 |
| 审查问题 | Yuxi 根据确定性规则发现的问题 | 严重等级、对象和证据 |
| 能力边界 | 当前快照是否允许某类计算 | “允许”与阻断原因 |
| 重算方案 | 基于来源副本计算出的候选结果 | 日期、浮时、关键标识及版本状态 |
| 来源版本 | 方案是否仍基于最新来源 | 必须为“当前版本”才能接受 |
| 审阅状态 | 用户是否已表态 | 待审阅、已接受、已拒绝 |
| 交付内容 | Candidate 生成后即可供业务流程读取的结果包 | 它不会自动改写来源计划，用户态度也不等于业务审批 |

### 4.1 审查和 CPM 重算不是同一件事

页面顶部的“零 Lag 已检查”“非零 Lag 未检查”来自来源审查规则；“CPM 重算”来自受限计算引擎。两者使用不同门禁：

- 审查统计回答“哪些来源关系已经过日期合规检查”；
- CPM 重算回答“当前整个输入是否落在已验证的计算 Profile 内”。

因此，审查中出现“非零 Lag 未检查”不能解释为所有关系都已验证，也不应仅凭这个数字判断 CPM 结果正确或错误。Lag 日历策略已冻结后，单一有效项目日历中的非零正负 Lag 关系会按统一项目日历工作分钟真正检查，此时“非零 Lag 未检查”通常为 0；策略未冻结的旧快照或日历口径不支持的场景仍显示为未检查并上报阻断问题。

## 5. 页面区域说明

### 5.1 来源快照列表

每个快照显示外部项目标识、外部版本、提交时间和快照 ID 简写。

操作建议：

- 测试前记录所选项目标识和版本；
- 页面刷新后再次确认选中的快照；
- 不要仅凭相似项目名称判断版本，必须同时核对外部版本和时间。

### 5.2 外部 JSON 接入边界

Import 快照显示来源格式、Adapter 版本和三个阶段状态。规范化摘要只展示数量和原因：

- `preserved`：来源扩展字段已保存在私有来源对象；
- `ignored_for_audit`：这些字段没有参与 Yuxi Audit；
- `ignored_for_calculation`：这些字段没有参与 CPM；
- `unsupported`：当前 Adapter 或 Engine 明确不支持的来源语义。

“保留”不代表“已理解”，“接入成功”也不代表“CPM 允许”。以每个独立状态和原因代码为准。

是否允许来源审查或 CPM，以 Capability 为准；normalization report 用于解释字段如何处置。两者出现矛盾时，本次验收应判定失败并提交缺陷，不能选择其中一个继续。

### 5.3 项目概览

项目概览显示：

- 任务数和依赖数；
- 零 Lag 已检查数量；
- 非零 Lag 未检查数量；
- 阻断级问题数量；
- 开放起点和开放终点数量。

开放起点或终点不一定是错误。例如项目第一项任务通常没有前置关系，最后一项任务通常没有后续关系。应结合任务用途和 Issue 证据判断。

### 5.4 计划内容

快照详情中部展示来源计划事实，用于直接查看计划内容：

- 任务表：WBS、任务名称、类型（汇总/活动/里程碑）、工期、计划开始、计划完成；任务按层级缩进，汇总行浅色背景加粗。
- 轻量甘特图：按计划起止日期绘制的日历跨度条，周末灰显，汇总任务用浅色条、里程碑用菱形标记；长排期自动压缩列宽并支持横向滚动。

甘特条表示计划日期的日历跨度，不按工作日历折算，也不代表 CPM 计算结果；重算或优化后的最早/最晚日期、浮时和关键标识请在“排期重算/工期目标优化”方案抽屉中查看。

### 5.5 能力边界

能力边界包括甘特展示、来源排期审查、CPM 重算、资源均衡和资源成本优化。

测试 CPM 时只以“CPM 重算”的状态为准。资源能力被阻断不应影响当前 CPM 用例，也不能据此宣称资源能力已经实现。

### 5.6 审查问题

问题列表支持按严重等级和分类筛选。常用操作：

- “AI 审查计划”：从当前快照进入整份计划对话，汇总 Capability、Issue 数量、主要类别、证据和建议处理顺序；
- “证据”：查看规则来源、相关对象和直接上下游；
- “确认关系”：在汇总依赖或 inactive 依赖问题上进入关系确认工作台；
- “Agent 解释”：把已有审查事实带入具备 Schedule 工具的智能体，由智能体辅助解释。

Agent 只能解释已有审查证据，不应代替用户接受方案，也不能自行发明日期、Patch 或业务结论；来源 Validation 和 ignored/unsupported 字段不能被描述成已参与 Yuxi 审查或计算。“AI 审查计划”要求智能体同时启用 `get_schedule_review_context`、`get_schedule_audit` 和 `get_schedule_issue_context`；单 Issue“Agent 解释”只要求后两个工具。

### 5.7 排期重算

“生成重算方案”会基于当前来源快照创建独立候选结果：

- 成功时打开方案审阅抽屉；
- 不支持时显示阻断原因；
- 来源任务和来源计算字段都不会变化。

### 5.8 工期目标优化

“工期目标优化”用于比较明确授权范围内的有限工期方案，不会让 AI 自由修改排期。第一版支持：

- “在授权范围内尽早完工”；
- “满足目标完成时间”。

用户可以添加 1–10 个 active、自动、未开始的活动任务，并为每个任务分别填写业务已确认可实现的缩短后工期，再勾选明确授权。已完成、进行中、已有实际进度事实、inactive、手工或工期不大于 1 分钟的任务不会出现在授权列表中。系统比较基线以及这些授权任务的全部有限组合，并按主要目标选择方案；授权任务不能重复，也不能同时设为 locked task。可选的 locked tasks 会保持日期不动，依赖、Lag、日历、里程碑和任务模式始终不变。

成功时页面打开 Candidate，展示工期 Patch、完成时间、比较方案数量、最早/最晚日期、浮时和关键任务，并新增“方案对比”甘特。对比口径按方案类型区分：工期目标优化对比**引擎基线（未优化重算）与优化后**，排期重算对比**来源计划与重算结果**；每个任务两条条，日期有变化的任务深色描边，完成时刻用竖线标记。目标不可达时页面显示 `TARGET_FINISH_UNACHIEVABLE`，不会生成伪成功 Candidate。Candidate 生成后即可查看 Delivery；接受或拒绝只记录用户态度。

注意：引擎重算日期与来源计划日期是两种计算口径（例如里程碑在来源中可能是瞬时点，引擎按工期重算后项目完成会整体后移），不能直接拿“来源计划完成”与“引擎优化完成”比较；优化是否有效应以同一口径的“基线完成”与“优化完成”对比为准。

生成候选后，主页面“计划内容”卡片自动切换到“方案对比”模式（也可手动切换回“来源计划”），表格按方案类型追加基线/来源与优化/重算日期列，甘特叠加两条条，关掉抽屉也能直接看到优化效果。快照详情新增“已生成方案”卡片，列出当前快照的重算/优化候选（类型、有效状态、审阅态度、完成时间变化），刷新页面后可随时重新打开已生成方案。

“让 AI 帮我梳理目标与授权”只生成未发送的“工期优化规划”草稿。Agent 可以协助逐项确认目标、目标时间、授权任务、授权后工期和 locked tasks，但不能替用户填写工期、创建 Candidate 或提交请求；最终操作必须回到排期页面完成。

## 6. 重算方案审阅界面

### 6.1 顶部状态

| 页面字段 | 正常状态 | 说明 |
| --- | --- | --- |
| 候选结果 | 可审阅 | 方案通过技术校验 |
| 来源版本 | 当前版本 | 方案仍对应当前最新来源 |
| 审阅状态 | 待审阅 | 用户尚未接受或拒绝 |
| 变更类型 | 自动排期重算 | 当前方案来自 CPM 引擎 |

以下情况不要继续接受：

- 候选结果显示“不可应用”；
- 来源版本显示“已过期”；
- 页面显示阻断、加载失败或版本冲突；
- 任务名称、WBS 或日期明显不属于所选项目。

### 6.2 结果摘要

结果摘要包括：

- 受影响任务数量；
- 关键活动任务数量；
- 来源完成日期；
- 重算完成日期。

“关键活动任务”只统计活动任务，避免把关键汇总行重复计入。结果表仍可展示汇总任务的关键投影，便于观察阶段整体状态。

### 6.3 任务结果表

工期目标优化方案的审阅抽屉会尽量使用宽屏空间，减少任务结果表的横向滚动。表格以颜色和文字共同标识变化来源：绿色“工期已优化”表示该任务工期来自明确授权并被直接压缩；蓝色“日期联动调整”表示任务本身未被压缩，但开始或完成日期受到网络计算联动影响。直接优化任务同时发生日期变化时会同时显示两种标签。颜色只用于辅助扫读，判断时仍以标签、工期和日期字段为准。

| 列 | 含义 | 推荐检查方式 |
| --- | --- | --- |
| 任务 | 任务名称、WBS、汇总/变化标识 | 先确认任务身份，再看日期 |
| 来源计划 | 来源快照中的开始和完成 | 作为比较基线，不是引擎答案 |
| 最早日期 | 满足当前依赖、约束和日历后的最早开始/完成 | 判断任务最早可在何时执行 |
| 最晚日期 | 不延误候选项目完成日期时的最晚开始/完成 | 判断任务最迟可以移动到何时 |
| 总浮时 | 任务可推迟而不影响候选项目完成日期的工作时间 | 0 或更小通常表示关键 |
| 自由浮时 | 任务可推迟而不影响直接后续最早日期的工作时间 | 用于判断对直接后续的影响 |
| 关键任务 | 是否位于当前关键路径 | 红色“关键”需要优先关注 |

标签说明：

- “汇总”：该行来自直接子任务的日期和浮时投影，不参与依赖计算；
- “非活动”：该行显示来源日期，`calculation_status=excluded_inactive`，不应被解释为引擎重算日期；
- “日期有变化”：最早开始或完成与来源计划不同；
- “关键”：当前 `total_slack_minutes <= 0`；
- “非关键”：当前具有正总浮时。

### 6.4 技术明细

“查看技术明细（日期变化 Patch）”默认折叠。业务用户通常不需要打开它；测试人员排查字段映射、日期变化或交付问题时再查看。

技术明细不能替代页面主表，也不能要求普通用户通过阅读 JSON 判断方案。

## 7. 如何理解 CPM 结果

### 7.1 最早日期

最早日期表示在当前项目日历、任务工期、依赖关系和约束下，任务最早可以开始和完成的时间。

如果最早日期早于来源日期，通常表示来源计划保留了额外等待或尚未用关系表达的业务安排。不要直接接受，应确认等待是否有真实业务原因。

如果最早日期晚于来源日期，通常表示来源计划与依赖、约束或工作日历之间存在不一致，应优先检查相关关系。

### 7.2 最晚日期

最晚日期表示在不延误候选项目完成日期的前提下，任务最迟可以开始和完成的时间。

最晚日期不是建议把任务拖到最后，而是用于识别可用缓冲和关键程度。

### 7.3 总浮时

总浮时回答：“这项任务最多可以延后多少工作时间，而不推迟整个候选项目的完成日期？”

示例：

- `0 分钟`：没有可用总浮时，通常是关键活动；
- `480 分钟（8 小时）`：按当前项目日历约等于一个工作日总浮时；
- 总浮时很大：先检查任务是否属于孤立或弱连接网络，不要立即把它理解成可以任意推迟。

### 7.4 自由浮时

自由浮时回答：“这项任务最多可以延后多少工作时间，而不推迟直接后续任务的最早日期？”

可能出现：

- 总浮时大于 0、自由浮时为 0：任务可以延后，但会立即挤占后续任务的缓冲；
- 总浮时和自由浮时都大于 0：任务具有不会立即影响后续最早日期的局部缓冲；
- 两者都为 0：通常位于关键链路。

### 7.5 关键任务

关键任务的任何额外延误都可能推迟候选项目完成日期，应优先检查：

- 工期是否准确；
- 前后置关系是否完整；
- 正 Lag 是否是必要等待；
- 约束日期是否合理；
- 是否存在未表达在排期中的业务前提。

关键任务不等于“最重要的业务任务”。它是当前排期网络中的时间敏感任务。

### 7.6 汇总任务

汇总任务日期由直接子任务自底向上滚动：

- 开始取直接子任务最早开始；
- 完成取直接子任务最晚完成；
- 关键状态用于阶段级观察；
- 汇总任务本身不参与依赖计算。

如果来源计划让汇总任务直接参与依赖，当前 CPM 会明确阻断，需先由业务人员确认并规范化为合适的叶子任务关系。

### 7.7 非活动任务

非活动任务用于保留来源计划事实，不代表可由 Yuxi 继续计算的活动。Profile v15 只把 active 活动任务和里程碑放入 CPM 图，汇总日期也只滚动 active 子项。页面对 inactive 行使用灰化、虚线样式并显示来源日期；它不会产生关键标识、浮时、资源占用或可压缩工期。

如果来源依赖形成 `active → inactive → active`，系统不会猜测应把两端自动连成哪种关系。Dependency Workbench 会把触及同一 inactive 任务的来源边归为一个 Issue，用户必须明确选择 active 叶子前置和后置；Candidate 会同时移除已展示的来源边，再加入经确认的叶子关系。

## 8. 如何接受或拒绝方案

### 8.1 接受前检查清单

- [ ] 所选项目、外部版本和任务名称正确；
- [ ] 候选结果为“可审阅”；
- [ ] 来源版本为“当前版本”；
- [ ] 已检查来源完成与重算完成的差异；
- [ ] 已识别全部关键活动任务；
- [ ] 已抽查至少一个非关键任务的总浮时和自由浮时；
- [ ] 已确认明显变化的日期符合业务事实；
- [ ] 审阅意见说明了接受原因、适用范围和需要后续确认的事项。

Candidate 生成后即可查看 Delivery，来源快照始终不变。点击“接受”或“拒绝”只记录当前用户态度，不控制 Delivery 是否可读取，也不替代外部业务审批。

### 8.2 建议拒绝的情况

- 任务关系遗漏或连错；
- 工期、日历或约束与业务事实不一致；
- 关键路径与项目团队认知冲突且尚未查明原因；
- 来源日期包含真实等待，但排期网络没有表达该等待；
- 方案已过期；
- 结果虽可计算，但不适用于当前业务决策。

拒绝时应写清：对象、现象、期望、依据和影响，避免只写“结果不对”。

### 8.3 审阅意见示例

接受示例：

> 已核对 WBS 1.1–1.3 的任务关系和工期。关键活动与现场计划一致，非关键任务 B 的 480 分钟总浮时符合预期。本次接受仅表示认可候选结果，不代表已经回写业务系统。

拒绝示例：

> 拒绝。WBS 2.3 的材料确认必须在施工准备开始前完成，但来源快照缺少该 FS 关系，导致最早日期提前。请补充关系并提交新来源版本后重新计算。

## 9. 阻断结果如何处理

当页面显示“当前来源超出受支持的排期范围”时：

1. 记录项目标识、外部版本和测试时间；
2. 记录每个阻断代码、消息和前五个对象；
3. 判断是来源数据问题还是当前产品范围限制；
4. 不要手工忽略阻断后继续接受；
5. 将真实业务需求提交给产品和工程人员评估。

常见类型：

| 现象 | 处理建议 |
| --- | --- |
| 负 Lag | 单日历按统一项目日历计算；v2.4 多/任务日历按后续任务有效日历计算，不要手工换算成自然日 |
| 多/任务日历 | v2.4 明确项目默认、任务有效日历和 `SUCCESSOR_TASK_CALENDAR` 后可重算；字段缺失或互相矛盾时先修正来源 |
| 日历例外/继承 | 支持停工、连续停工、补班和父子覆盖；未知父日历、继承环、无工作时间、范围冲突或时区不一致时先修正来源 |
| 汇总依赖 | 使用“确认关系”明确应由哪些叶子任务替代 |
| inactive 任务依赖 | 使用“确认关系”同时核对全部来源边，并选择 active 叶子关系；不要手工假定自动跨接 |
| 实际进度 | 当前不要用重算方案替代进度更新和剩余工期分析 |
| 非法约束组合 | 修正来源约束后提交新版本 |

## 10. 测试前准备

### 10.1 测试角色

建议至少包含：

- 1 名熟悉原排期的计划人员；
- 1–3 名需要阅读排期结果的项目用户；
- 1 名负责记录证据的测试人员；
- 必要时安排 1 名系统管理员准备快照和测试账号。

### 10.2 测试数据

准备三类数据：

1. **外部 Import 样例**：带已注册 `schema_version`，用于验证接入、规范化和边界展示；
2. **受支持 CPM 样例**：统一项目日历、无汇总依赖，可包含已确认语义的负 Lag，用于验证完整重算和审阅流程；
3. **明确阻断样例**：至少包含一种已知范围外输入，用于验证系统不会近似计算。

业务验收必须使用已脱敏且任务名称可读的代表性业务快照。合成或工程演示样例可以验证页面和协议，但不能替代独立真实业务案例。

仓库中的 `Yuxi_复杂排期测试套件_v1/*/input.json` 使用测试专用协议 `schedule_engine_test_input_v1`，不能直接在页面上传。需要验证页面时，先按 [15.7 将复杂套件导出后导入页面](#_15-7-将复杂套件导出后导入页面) 生成 Canonical JSON；需要验证完整 C01–C08 冻结结果时，运行 [15.6 C01–C08 冻结复杂套件](#_15-6-c01-c08-冻结复杂套件)。

### 10.3 测试环境检查

- 页面能够正常登录；
- “排期审查”导航可见；
- 目标账号能看到测试快照；
- API、Web 和 Worker 服务健康；
- 测试期间不修改来源业务系统中的同一版本；
- 截图、日志和反馈中不包含密码、Token、API Key 或未脱敏业务信息。

### 10.4 每个用例的证据

至少记录：

- 用例编号；
- 测试账号或角色；
- 项目标识和外部版本；
- 操作时间；
- 实际结果；
- 页面截图；
- 是否通过；
- 问题编号或反馈编号。

## 11. 用户验收测试用例

### UAT-01 查看来源快照

**前置条件**：测试账号下至少有一个已提交快照。

**步骤**：

1. 进入“排期审查”；
2. 在左侧选择目标快照；
3. 核对项目名、版本、任务数和依赖数。

**预期结果**：页面展示正确项目，出现“只读来源快照”，无跨用户数据；Import 快照同时显示外部接入边界卡片。

### UAT-02 理解审查概览

**步骤**：记录零 Lag 已检查、非零 Lag 未检查、阻断问题和开放起点/终点数量。

**预期结果**：用户能解释这些数字分别表示什么，不把“未检查”误读为“已通过”。

### UAT-03 查看问题证据

**步骤**：选择一个 Issue，点击“证据”，查看对象和直接上下游。

**预期结果**：证据与问题行一致，用户能指出受影响任务或关系。

### UAT-04 生成受支持重算方案

**前置条件**：“CPM 重算”显示允许。

**步骤**：点击“生成重算方案”。

**预期结果**：打开“排期重算方案审阅”；候选结果为“可审阅”，来源版本为“当前版本”，审阅状态为“待审阅”。

### UAT-05 核对任务和日期

**步骤**：抽查至少 3 个活动任务和 1 个汇总任务，比较来源、最早和最晚日期。

**预期结果**：任务名称/WBS 正确；日期完整；汇总行有“汇总”标签；发生变化的任务有“日期有变化”标签。

### UAT-06 识别关键与非关键任务

**步骤**：找到至少一个关键活动和一个非关键活动，说明判断依据。

**预期结果**：关键活动总浮时为 0 或更小；非关键活动具有正总浮时；用户不把“关键”误解为业务重要性。

### UAT-07 区分总浮时和自由浮时

**步骤**：选择一个两类浮时不同的任务，解释其对项目完成和直接后续的影响。

**预期结果**：用户能够正确区分“影响项目完成”和“影响直接后续最早日期”。

### UAT-08 验证技术明细默认折叠

**步骤**：打开重算方案，不点击“查看技术明细”。

**预期结果**：用户可通过结构化表格完成主要判断，页面默认不展示 Patch JSON。

### UAT-09 接受方案

**步骤**：填写接受原因并点击“接受”，随后查看 Delivery。

**预期结果**：审阅状态变为已接受；仍可读取生成时已经存在的交付内容；来源快照没有被修改。

### UAT-10 拒绝方案

**步骤**：对另一份方案填写具体拒绝原因并点击“拒绝”。

**预期结果**：审阅状态变为已拒绝；拒绝不删除来源快照，也不修改任务日期。

### UAT-11 验证范围外输入

**前置条件**：准备包含日历继承环、冲突例外、缺失有效日历或汇总依赖的样例。

**步骤**：选择样例并点击“生成重算方案”。

**预期结果**：页面显示结构化阻断原因，不生成近似日期，不打开可接受的重算方案。

### UAT-12 验证来源不可变

**适用角色**：技术测试人员。

**步骤**：

1. 记录生成方案前的 `canonical_snapshot_sha256`；Import 快照同时记录 `source_document_sha256`；
2. 生成方案并接受；
3. 重新读取 Canonical 来源 Snapshot 和两个内容哈希。

**预期结果**：前后 Canonical 哈希一致；Import 的来源文档哈希也一致；计算日期只存在于候选结果和交付内容中。`source_document_sha256` 是来源 `document` 的排序紧凑 JSON 哈希，不是 MPP 文件哈希或原始 HTTP 字节哈希。

### UAT-13 验证版本过期保护

**适用角色**：技术测试人员。

**前置条件**：在旧方案生成后，为同一外部项目提交新的来源版本。

**步骤**：通过 Candidate 详情接口重新读取旧方案。

**预期结果**：来源版本显示已过期，旧方案的 Delivery 仍可读取和追溯，但 `application_allowed=false`，不能把它作为当前版本应用。

### UAT-14 验证用户隔离

**适用角色**：技术测试人员。

**步骤**：使用另一个普通账号访问原账号的 Snapshot ID。

**预期结果**：列表不可见，直接访问返回不可见/不存在语义，不泄露其他用户数据。

### UAT-15 验证表格可用性

**步骤**：在常用屏幕尺寸下查看完整表格，并横向滚动至“关键任务”列。

### UAT-16 验证外部 JSON 导入边界

**适用角色**：测试人员、接口维护人员。

**前置条件**：通过 `/api/schedule/imports` 提交一个已注册来源版本。

**步骤**：

1. 核对来源格式和 Adapter 版本；
2. 分别记录“外部接入”“来源审查”“CPM 重算”状态；
3. 记录 preserved、ignored 和 unsupported 数量及原因；
4. 检查 Capability 与 normalization report 是否一致；

**预期结果**：三个状态互不混淆；接入成功不会被解释成提取可信或所有语义已参与计算；Capability 与报告无矛盾；页面不展示未知字段值；Agent 只生成带 YUXI_AUDIT 边界的草稿。任一状态或报告矛盾都应记录为缺陷，不能按通过处理。

### UAT-17 验证整份计划 AI 审查

**前置条件**：当前用户拥有一个已完成 Audit 的 Snapshot；至少一个可访问智能体同时启用 `get_schedule_review_context`、`get_schedule_audit` 和 `get_schedule_issue_context`。

**步骤**：选择 Snapshot，点击“AI 审查计划”，选择智能体；核对项目、外部版本和 Snapshot 简写；分别选择“概括主要问题”“解释能力阻断”“建议处理顺序”，确认都只更新草稿；发送其中一个问题，打开回答中的 Issue 证据链接；随后切换到其他线程。

## 14. 常见问题

### 14.1 为什么看不到任何来源快照？

快照按提交用户隔离。确认当前账号、提交账号和环境是否一致，并确认业务系统已成功提交数据。

### 14.2 为什么“CPM 重算”显示允许，审查列表仍有 Warning？

Capability 和 Issue 严重等级是不同维度。Warning 可能是 Baseline、状态日期、里程碑或开放网络提示，并不一定阻断当前 Profile；仍需逐条审阅。

### 14.3 为什么点击生成后没有方案？

当前快照可能超出支持范围。查看页面阻断代码、消息和对象，不要要求系统忽略阻断生成近似日期。

### 14.4 为什么重算完成日期比来源完成日期早很多？

常见原因包括来源计划中存在未用关系表达的等待、任务网络不完整、开放起点/终点较多或来源汇总日期包含额外缓冲。应先审查网络和业务等待，不要仅因日期更早就接受。

### 14.5 为什么某个任务浮时特别大？

先检查它是否缺少前置或后续、是否属于孤立网络、是否与项目最终完成节点连接。大浮时可能是网络结构问题，不一定是真实可用缓冲。

### 14.6 为什么汇总任务和子任务都显示关键？

汇总任务的关键状态是子任务结果的阶段级投影。顶部“关键活动任务”只统计活动，避免重复计数。

### 14.7 为什么接受后来源计划没有变化？

这是正确行为。接受只记录审阅态度；系统不会原地修改 Source。正式回流需要受控 Delivery 和新来源版本流程。

### 14.8 为什么接受按钮不可用？

通常因为候选结果不可应用或来源版本已过期。重新选择最新来源、修正输入问题并生成新方案。

### 14.9 Delivery 是什么？

Delivery 是供后续业务流程读取的交付内容，包含方案、版本状态和计算结果。当前页面查看 Delivery 不会自动回写来源系统。

### 14.10 可以直接上传 MPP 文件吗？

当前不可以。业务系统或转换服务必须先从 MPP 提取带已注册 `schema_version` 的来源 JSON，再调用 `/api/schedule/imports`；已经能够生成完整 Canonical 的调用方也可以继续使用 `/api/schedule/snapshots`。Yuxi 核心服务不读取 MPP，也不依赖 Windows。

### 14.11 来源 JSON 可以包含额外字段吗？

可以。外部 Import 文档允许未知字段并保存在私有来源对象中，但未知字段不会自动参与 Audit 或 CPM。已定义核心字段缺失或类型错误仍会被拒绝。内部 `canonical_schedule_v2.2` 至 `canonical_schedule_v2.8` 都保持严格。

### 14.12 可以计算资源冲突和成本吗？

可以，但必须直接提交强类型 Canonical v2.7，并提供可追溯的 Resource、Assignment、units、max units 和标准小时费率。系统会在 CPM 之后检测超配区间，并按 `duration_minutes × units / 60 × standard_rate_per_hour` 输出 Assignment 成本数值。当前契约没有币种字段，因此不显示或猜测币种；自动资源均衡、资源成本优化和多项目统筹仍不支持。

### 14.13 可以把结果写回 MPP 吗？

Yuxi 当前不写回 MPP。需要回写时，由外部业务系统或独立转换服务读取受控 Delivery，在新的来源副本上应用，并生成新的 MPP 或业务版本；随后重新提取 JSON 作为新版本回流 Yuxi。

### 14.14 当前结果能直接用于生产吗？

不能仅凭当前工程门禁直接宣称生产通用性通过。生产前仍需独立真实案例、正式适配器约定、回流追溯、失败恢复和完整业务验收。

### 14.15 “来源审查允许”是否代表 MPP 提取正确？

不代表。它只说明 Yuxi 能基于内部 Canonical 执行确定性 Audit。Yuxi 当前不读取 MPP，也不会复算外部声明的 `mpp_sha256`；外部转换服务必须自行提供保存、重开、重算、字段比对和 manifest 哈希证据。

### 14.16 工期目标优化会修改哪些内容？

只会在 Candidate 副本中缩短用户明确授权的自动活动任务工期。依赖、Lag、日历、里程碑、任务模式和来源 Snapshot 都不会被修改。若来源为 v2.7，Candidate 会重新分析授权工期组合对应的资源冲突和成本，但不会自动调整 Assignment 或执行资源均衡。

### 14.17 为什么目标不可达时没有 Candidate？

这表示全部有限授权组合都无法满足目标。系统返回 blocker 和最佳可达策略供用户调整目标或重新取得业务授权，不会把未满足目标的结果包装成成功 Candidate。
